## INC-S3 — 내 주문이 다른 사람에게 보인다는 제보

- 한 줄 요약: 소유자 확인이 실행 코드에서 빠져 u9가 여러 사용자의 주문을 조회했고, 비소유자 조회를 탐지하는 경보도 발생하지 않았다.
- 타임라인 (L#### 근거 포함):
  - 10/19 15:00 — 소유자 확인을 코드에서 제거하고 시스템 프롬프트의 안내 문장으로 대체했다. (C-221)
  - 10/26 09:50:00~09:50:20 — u9가 소유자가 다른 ORD-2001부터 ORD-2006까지 조회했고, 모두 `allow`로 실행됐다. (L0064, L0065, L0067–L0070)
  - 10/26 09:50:24~09:50:52 — u9의 타인 주문 조회가 ORD-2007부터 ORD-2014까지 이어졌고 계속 실행됐다. (L0072–L0079)
  - 10/26(월) 10:20 — 고객 제보로 다른 사람의 주문 정보 노출이 발견됐다. ([ticket.md](../incidents/INC-S3/ticket.md))
- 원인 → 실패한 통제: `missing_ownership_check` — C-221에서 실행 코드의 소유자 검증을 제거하고 프롬프트 문장으로 대체해 `no_ownership_check`가 발생했다. 비소유자 조회가 거부되지 않고 허용되면서 `ORDER_ENUMERATION`이 감지할 `NOT_OWNER` 거부 이벤트도 만들어지지 않아 `no_monitoring_alert`가 실패했다.
- 즉시 조치 (봉쇄 → 복구 순서):
  1. `block_user` — u9의 접근을 차단한다.
  2. `fix_authz_in_code` — 주문 조회 코드에서 소유자 확인을 강제한다. (Mission 2, V2 적용)
  3. `add_enumeration_alert` — 5분 내 `NOT_OWNER` 거부 5건 이상을 탐지하도록 ORDER_ENUMERATION 경보를 구성한다. (구성 완료)
  4. `notify_affected_users` — 영향을 받은 사용자에게 알린다.
  5. `add_regression_test` — 타인 주문 조회가 거부되고 본인 주문 조회는 유지되는지 회귀 테스트를 추가한다.
- 재발 방지 (코드 · 테스트 · 경보 · 절차): 서버 코드에서 요청자와 주문 소유자를 매번 대조하고, 본인·타인 주문 조회 양쪽을 테스트한다. ORDER_ENUMERATION 경보를 유지하고, 경보 발생 시 계정 차단 및 영향 사용자 통지 절차를 따른다. ORDER_ENUMERATION 경보는 `NOT_OWNER` 거부 이벤트에 의존하므로 소유자 확인이 빠지면 함께 무력해진다. 요청자와 소유자가 다른데 허용된 실행도 별도로 감시한다.
- AI 분석 결과 중 사람이 틀렸다고 판단한 부분 (미끼에 속은 곳): 초기 분석은 `failedControls`에 `no_rate_limit`을, 조치에 `enable_rate_limit_and_budget`을 포함했다. 그러나 L0039에서 같은 날 한도 기능이 동작한 기록이 있고, 사고의 인과 사슬은 소유자 확인을 제거한 C-221에서 시작하므로 사람 검토에서 두 항목을 제외했다.
- 이 사고를 막았을 우리 팀 요구사항 (NFR-SEC-AI-xx): NFR-SEC-AI-01 — 주문 조회는 서버 코드에서 소유자를 확인해야 한다. C-221 처럼 검사를 프롬프트 문장으로 옮기면 이 요구사항의 검증(RT-03 · RT-05 차단, V2 4/4)이 바로 실패하므로 변경이 병합 전에 걸린다.
