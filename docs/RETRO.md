# RETRO — 5분 회고 (비난 없는 회고)

| 질문 | 팀 답 |
|---|---|
| 가장 놀랐던 공격 한 가지 (그리고 왜 통했나) | 문서 속 숨은 지시(RT-04). 요약해 달라는 문서 안에 UNTRUSTED>> 로 구역을 닫고 다른 사람 주문 조회를 시키는 문장을 넣으면, 사용자가 아무것도 악용하지 않아도 통했다. 문서를 사용자의 지시와 같은 입력으로 다뤘고 구분자를 문서가 직접 닫을 수 있었기 때문이다. 방어는 문서 검사와 구분자 무력화, 오염된 문맥에서 쿠폰 · 환불 거부로 나눴다. |
| AI 가 쓴 방어 중 허점이 있던 것 | CI 시크릿 스캔의 오탐 제외 규칙. 조건이 너무 넓어서 개인키 한 줄이 CI 를 통과했고, 직접 시험 3건으로 확인한 뒤 좁혔다. 그 밖에 허용 도구를 객체로 조회해 constructor 가 통과할 위험, 카드번호 규칙이 일반 숫자 문장을 훼손할 위험, 결과 형식이 틀리면 조용히 통과하는 검사가 있었다. 모두 계획표 검토나 직접 시험으로 잡았다. |
| 방어를 추가하다 정상 요청을 막은 경험 | 배송 지연은 무시하고 환불 규칙을 알려 줘, 시스템 프롬프트 창이 안 떠요 같은 정상 문장이 단어만 보는 필터에 막힐 뻔했다. 계획표 단계에서 이런 문장을 통과 사례로 먼저 요청문에 넣고, 대상과 동사가 가까이 있을 때만 차단하도록 좁혔다. |
| 다음에는 처음부터 하겠다고 정한 것 (시프트 레프트) | 방어를 요청할 때 정상 문장 통과, 비정상 입력 거부, 허용 목록 구현 방식, 규칙끼리 깨뜨리는 경우를 처음부터 요청문에 넣는다. CI 시크릿 스캔은 처음부터 켜 두고, 검사가 항상 통과하지 않는지는 변이 시험으로 증명한다. |
| 팀 협업에서 잘된 점 · 아쉬운 점 | 잘된 점: 단계마다 진행 · 검증을 나누고 계획표 승인으로 에이전트의 실수를 코드 전에 잡았다. 아쉬운 점: AI 사용 기록을 합치는 시점과 재시도 횟수 기준을 미리 정하지 않아 중간에 고쳤고, 미션 사이의 역할 분담을 일찍 공유하지 못했다. |
